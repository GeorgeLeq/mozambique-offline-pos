2. Security (Protecting the Offline Environment)
Because the SQLite file (sqlite.db) is physically sitting on the user's Windows machine, an advanced, malicious employee could theoretically open it with a tool and edit the data.
Strict PIN Authorization: We must ensure that every sensitive action (Voids, Manual Discounts, Payouts, Inventory adjustments, Shift closures) strictly requires a Manager PIN prompt, and logs an Audit Event immediately.
Anti-Tampering (Future Proofing): In the future, we might want to look into SQLCipher for Tauri to fully encrypt the local database. For now, a good trick is adding a "Hash" column to receipts. When a sale is made, we hash the total + items. If the user edits the SQLite file manually to lower the total, the hash will break, and our Cloud Sync engine can flag it as "Tampered".
System Time Manipulation: Cashiers sometimes change the Windows clock to backdate sales or cheat shift hours. When the app is online, we should silently check the real time against the Windows time to flag anomalies.
3. Speed & Optimization
SQLite Indexes: This is the #1 secret to a fast offline app. We need to ensure our database schema has INDEXES on columns we query often. For example, created_at on Sales, status on Debts, and product_id on everything. Without indexes, SQLite will scan the whole table every time the MiniDashboard refreshes.
Sync Engine Batching: If the internet goes down for 3 days, a busy shop might have 3,000 pending sales. When the internet comes back, our syncAllToCloud function shouldn't send 3,000 individual requests to Supabase (that will freeze the app). It needs to send them in "Batches" of 100.
Barcode Scanner Latency: On the Cashier screen, when a barcode is scanned, the item must appear in the cart instantly (under 50ms). We must ensure the cart state doesn't cause the entire page to re-render.

1. Data Security & Local Storage (SQLite & Tauri)
Risk: In Tauri desktop applications, the local SQLite database file is stored in the user's AppData directory. If the physical machine is stolen or accessed without authorization, sensitive local records (customer debts/fiado, cash drawer logs, sales history) could be read if unencrypted.
Mitigation: Ensure that SQLite uses SQLCipher or Tauri’s secure local storage extension where applicable, and implement OS-level file permissions. Avoid storing plaintext master passwords, manager override PINs, or Supabase service role keys in localStorage or plaintext config files.

2. Authentication, Cashier PINs, & Role-Based Access Control (RBAC)
Risk: Cashiers often share terminals or log in quickly using 4-digit PINs. If PINs are stored in plaintext in SQLite or if manager override permissions (for voids, manual discounts, and till payouts) are insufficiently validated, rogue staff could authorize fraudulent discounts or cash refunds.
Mitigation:
Ensure cashier and manager PINs are hashed (e.g., using bcrypt or Argon2) before saving to SQLite.
Implement strict frontend and backend state checks requiring explicit manager re-authentication (PIN/password verification) for sensitive actions like manual overrides, till payouts, and blind closes.

3. Supabase Cloud Sync & Row Level Security (RLS)
Risk: When syncing offline SQLite transactions to Supabase, anonymous or insufficiently restricted API requests could lead to data leakage or unauthorized data tampering across different shop branches.
Mitigation:
Enforce strict Row Level Security (RLS) policies on all Supabase tables so that each storefront/tenant can only read/write their own branch data.
Only expose the Supabase anon key on the client side; never embed the service_role secret key in client bundles or Tauri frontend code.

4. Tauri IPC & Content Security Policy (CSP)
Risk: Modern desktop apps built with web technologies can be vulnerable to Cross-Site Scripting (XSS) if external scripts or unsafe HTML are rendered.
Mitigation:
Configure a strict Content Security Policy (CSP) in tauri.conf.json to disallow unauthorized external script execution and inline script injections.
Limit Tauri capability scopes (capabilities/) to only allow necessary filesystem, plugin-sql, and printing permissions.

5. Mozambique Fiscal Compliance & Audit Trails
Risk: Retail POS systems in Mozambique must maintain tamper-evident audit trails for tax authorities (Autoridade Tributária de Moçambique - AT) regarding VAT (IVA), sales receipts, and shift closures.
Mitigation:
Our audit logging module (src/lib/audit.ts) must ensure that sales, cancellations, and till adjustments are immutably recorded with timestamps, cashier IDs, and sequential invoice numbering so receipts cannot be silently deleted or edited post-checkout.

1. PIN Hashing & Authentication (src/lib/security/crypto.ts)
What is currently implemented:
We have hashPin() in src/lib/security/crypto.ts, which uses Web Crypto's SHA-256 with a static salt (_mozpos_salt_2026).
When adding or updating employees via the Employee Manager, new PINs are saved with this hash.
The Gaps:
Not a Slow/Stretching Hash: SHA-256 is fast. Because retail PINs are short (usually 4 to 6 numeric digits = 10,000 to 1,000,000 combinations), an attacker with a copy of the hash could brute-force the PIN in seconds using standard hardware. Upgrading to a key-stretching function like PBKDF2 (or bcrypt) with 100,000 iterations makes brute-forcing computationally prohibitive.
Legacy Plaintext Fallback: verifyPin still accepts raw plaintext PINs (if (inputPin === storedHash) return true) for backward compatibility with early records.

The file itself (pos.db) is standard unencrypted SQLite.

1. How Does the Provider's Phone Send the Airtime/Megabytes to the Customer?
In Mozambique, telecom operators (Vodacom and Movitel) have direct USSD transfer codes that any SIM card can run.
There are two methods of dispatching:
Method A: Direct Balance / Airtime Transfer ("Txuna / Transfere Saldo")
Vodacom Direct Transfer:
USSD Code: *100*3*{recipient_phone}*{amount}*{pin}#
(e.g., *100*3*841234567*50*1234# instantly transfers 50 MT balance to that phone)
Movitel Direct Transfer:
USSD Code: *150*... or *131*{recipient_phone}*{amount}*{pin}#
Method B: Buying a Bundle for Another Person ("Oferecer Pacote / Megas")
Both Vodacom and Movitel allow one number to buy a data package directly for another number:
Vodacom (Tudo Num Só / Internet):
USSD: *111# -> Select "Internet" -> Select "Oferecer a um amigo" -> Enter Customer Number -> Select Package -> Confirm.
(In our Android app, the USSD Runner sends string sequences like *111*2*1*{recipient}*1# or dials interactively using the Android Accessibility Service).
Movitel (Mega Net):
USSD: *155# -> "Comprar para outro número" -> Enter Number -> Select 1 GB -> Confirm with PIN.
How the Android App executes this with Zero Human Effort:
When an order is verified in Supabase, a task enters dispatch_queue with the exact USSD command:
